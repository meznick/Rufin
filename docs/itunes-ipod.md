# iTunes и iPod в Rufin — документация подсистемы

Живой обзор подсистемы «iTunes + iPod»: iTunes-источник (чтение `.itl`, двухсторонняя
синхронизация статистики) и iPod-интеграция (страница устройства, libgpod, синк).
Обновлён 2026-11-13.

Границы документа. Форматные исследования (офсеты, семантика полей, проверки на
реальной библиотеке) остаются в репозитории `itl-player` — `NOTES.md` §17–20 и
`docs/LIBGPOD.md`; здесь они не дублируются, только ссылаются. Задачный уровень —
верификация, результаты, долги — живёт в SDD-артефактах этого репозитория
(`spec.md`, `plan.md`, `tasks.md`, `deltas/`). Этот документ — карта подсистемы:
архитектура, правила безопасности, тестовые корпуса, состояние и дорожная карта.

## 1. Терминология

| Термин | Определение |
|---|---|
| `.itl` (`iTunes Library.itl`) | Бинарная библиотека iTunes: конверт AES-128-ECB + zlib, внутри little-endian iPod-DB-подобные блоки. Единственный источник правды; XML — экспорт, никогда не читается обратно. |
| `mith` | Элемент-трек в `.itl`; все поля трека (рейтинг, счётчики, даты, PID, explicit и т.д.) живут в нём. |
| `mhoh` | Элемент-строка в `.itl`; типы 0x65/0x66 несут smart-правила плейлистов (`SLst`-блоб). |
| `iTunesDB` | Музыкальная БД на iPod: `mhsd`/`mhlt`/`mhyt`/`mhlp`; трек = `mhit`, плейлист = `mhyp`, член плейлиста = `mhip`. |
| `ArtworkDB` / `ithmb` | БД обложек на iPod и файлы миниатюр (`.ithmb`); без них обложки в стоковой прошивке не работают. |
| `SysInfo` / `SysInfoExtended` | Файлы в `iPod_Control/Device/` (модель, FireWire ID); после восстановления устройства часто пустые. |
| `dbid` | Числовой идентификатор трека на устройстве (`mhit` @0x70). Равен PID хоста. |
| PID (track Persistent ID) | Стабильный идентификатор трека: `mith` @0x80 в `.itl` = `Track ID` в XML = device dbid. |
| sentinel | Маркер iTunes внутри `.itl`: ноль = библиотека открыта в iTunes (писать нельзя), ненулевой = закрыта, отсутствует = никогда не открывалась. |
| Apple-эпоха | Секунды с 1904-01-01 в локальном wall-clock (без TZ). Даты в `.itl` и на устройстве сравниваются в этом пространстве; конвертация — только на границе записи через itl-sync. |
| On-The-Go (OTG) | Плейлист, созданный пользователем прямо на iPod без iTunes — часть медиатеки устройства, а не просто очередь. Активная очередь живёт в `OTGPlaylistInfo` (libgpod отдаёт её как `OTG Playlist N`); при синке iTunes переносит её в библиотеку как `On-The-Go N`. Сохранённые OTG-плейлисты — обычные плейлисты (см. §6). |
| boundary-minus-1 | Кодировка порогов в smart-правилах: «rating > 3.5★» хранится как `GreaterThan 69`, а не 70. |
| материализованный список | Кэш членов smart-плейлиста (записи `mtph`/`mhip`), который iTunes пересчитывает при открытии библиотеки/синке. Правда — критерии, список — кэш (см. §6). |
| fill-down (album rating) | iTunes проставляет рейтинг альбома в треки с нулевым рейтингом в экспорте; в `mith` сырой ноль при этом не пишется. Оценка smart-правил идёт по эффективному значению. |
| dry run | Расчёт дельт синка без записи на устройство, без потребления статистики устройства и без записи в хост-`.itl`. |
| FSM | Конечный автомат подключения (пять состояний, см. §4). |
| preflight | Немутирующие проверки готовности устройства к синку. |
| корпус (corpus) | Env-gated снапшот реальных данных (копия `.itl`, дерево устройства) для тестов; продакшн-данные тестами не трогаются никогда. |

## 2. Архитектура

Крейты и роли:

- `crates/sources` — iTunes-источник: `src/itunes/mod.rs` (конфиг, sentinel, источник),
  `catalog.rs` (чтение каталога из `.itl`), `write.rs` (write-back). Зависит от
  `itl-core` 0.1.1 (форматные ридеры) и `itl-sync` 0.1.0 (маппинг путей, запись) —
  оба опубликованы на crates.io, MIT.
- `crates/ipod` — безопасная обёртка над libgpod: `backend.rs` (dlopen + ABI-проверка),
  `session.rs` (`DeviceSession`, owned-результаты), `artwork.rs` (вердикт обложек),
  `write.rs` (write-API, за гейтом), `treehash.rs` (доказательства немутирующих чтений),
  `testkit.rs`, `ffi/`. Единственное место в процессе, которое касается libgpod.
- `crates/ipod-sync` — ядро синка: `discovery.rs` (нулевая запись), `mounts.rs`,
  `preflight.rs` (матрица готовности), `retrieval.rs` (DeviceInfo),
  `mapping/{host,map,smart,mod}.rs` (B-008). Зависит от `ipod`, `itl-core`, `itl-sync`.
- `crates/gtk-library` — `device_manager.rs` (типы B-002), сервис `IpodConnection` и
  `IpodMountMonitor` (B-006), клей FSM.
- `crates/rufin-core` — `source/itunes_sync.rs`: debounced write-back в `.itl`.
- `crates/gtk-preferences` — экран настроек iTunes-источника
  (`preferences/source/login/itunes.rs`).

Внешние зависимости:

- **libgpod 0.8.3** (C, LGPL-2.1-or-later) — чтение/запись `iTunesDB`/`ArtworkDB`,
  генерация моделе-специфичных чексумм. Загружается в рантайме (`dlopen`), сборка без
  бэкенда возможна и обязана сообщать «Sync unavailable», а не падать на копирование
  файлов. Сборка пинится `scripts/build-libgpod.sh` (таск и патчи Arch 0.8.3-20,
  sha256-проверка, ABI-маркер `rufin-libgpod.abi`; рецепт — `itl-player/docs/LIBGPOD.md`).
- **itl-core / itl-sync** — хостовая сторона: чтение `.itl` и единственная точка записи
  (атомарная запись, rolling-бэкапы, отказ по sentinel). Подробности в `itl-player`.

Потоки данных:

- Чтение: `.itl` → (itl-core) → каталог iTunes-источника; медиа-пути через маппинг
  itl-sync (поле 511 `.itl` / родитель `.itl`), URI-форма авторитативна.
- Запись в хост: UI-действия → дебаунс → `itl_sync::write_library` (один батч = одна
  атомарная запись).
- Устройство: parse `iTunesDB`/`ArtworkDB` через `crates/ipod` → owned-модели →
  сравнение с хостом (B-008) → дельты → (после B-010) запись через libgpod.

## 3. iTunes-источник

Состояние: реализован и слит в `fork-master` (2026-10, «iTunes source with two-way
.itl sync, explicit badge and star ratings»). Дизайн и реестр патчей — `itl-player`
`NOTES.md` §17–18.

- **Чтение**: каталог из `.itl` через itl-core; встроенные обложки через
  `inspect_embedded` батчами по 64 файла с ревизионным кэшем. Кэш `.itc2` в
  `Album Artwork/` проанализирован и не используется (`NOTES.md` §3.5.6).
  Плейлисты iTunes (импорт статических и smart из `mlph`/`miph`) — в очереди.
- **Идентичность**: трек = PID (`mith` @0x80); альбомы = пара (имя, album artist) —
  поле album-id в `.itl` непригодно (`NOTES.md` §18).
- **Write-back**: один вызов `itl_sync::write_library` на батч (in-process, v2,
  `spawn_blocking`, debounced); патчи — рейтинг (округление до целой звезды при
  коммите), play count, skip count, last played, explicit (`TrackPatch.explicit`
  готов и принят в VM; set/clear из UI — в очереди).
- **Sentinel**: нулевой sentinel = библиотека открыта в iTunes → отказ в записи без
  обходов; UI показывает отказ (старт и попытка действия). Второй слой — скан
  `/proc` на открытые хэндлы.
- **UI**: экран настроек источника (правка library/media folder существующего
  источника; `tz_offset_seconds` в UI не выносится); интерактивная колонка звёзд
  рейтинга (клик/драг коммитит, все источники); бейдж explicit «E» (display-only,
  `TrackPresentation::explicit()`, CSS-класс `explicit-badge`); редактор метаданных
  через arm `Implementation::Itunes` в `NativeFile::resolve`.
- **Ограничения владельца**: никакого одновременного iTunes — опроса нет (pull при
  старте/ручном refresh, push по событию).

## 4. iPod: подключение и FSM

Состояния (`ConnectionState`, контракт B-002): `Disconnected`, `Connecting`,
`BackendUnavailable` (метка UI «Sync unavailable»), `Ready`, `Error`. Синк включён
только в `Ready`; в `Ready` можно попасть только через preflight-путь
(`set_ready_after_preflight()`), прямой прыжок заблокирован. Ready — не транзакция и
не постоянный замок: на границе записи готовность и конкурирующие писатели
перепроверяются.

- **Discovery** (B-003): только уровень ФС — mount с каталогом `iPod_Control/` в
  корне; ни парсов, ни сессий (parse-пути libgpod могут создавать `Artwork/` на живых
  деревьях — `deltas/b007_delta.md` §1.1). Нулевая запись доказана tree-hash тестом.
  Кандидат никогда не помечается Ready.
- **Мониторинг** (B-006): gio `VolumeMonitor` → 300 мс дебаунс → скан; без
  периодического опроса (решение владельца). Парсы libgpod — на сериализованном
  worker-потоке, GTK main loop не блокируют. `Connecting` эмитится при детекции,
  до parse.
- **Retrieval** (B-005): имя = имя master-плейлиста из `iTunesDB` (type-1 `mhyp`;
  volume label — производная uppercase-копия, фолбэка нет); модель/поколение —
  из `SysInfo` (`ModelNumStr`) через модельную таблицу libgpod; ёмкость — из
  filesystem stats, не из номинальной `Itdb_IpodInfo.capacity`. Пустой `SysInfo` =
  нормальное состояние свежевосстановленного iPod → модель неизвестна, без
  изобретения значений.
- **Preflight** (B-004), порядок проверок (первая ошибка выигрывает): read-only mount →
  parse БД → модель разрешена → поддерживаемый набор (Video 5/5.5G + Classic
  6/6.5/7G) → FireWire ID для Classic (чексумма обязательна даже по USB; у Video
  такого требования нет) → вердикт обложек. Без Trust/pairing (Video/Classic — не
  iOS, usbmuxd не нужен). Отсутствующая прошивка сама по себе Ready не блокирует.
- **Модельная политика** (решения владельца 2026-11-10, `deltas/b006_delta.md`):
  unsupported/unresolved модели и Classic-без-FireWire доходят до Ready; вердикты
  `model_supported`/`checksum_possible` едут в `DeviceFacts`/`DeviceInfo` для
  гейтинга UI; preflight отказывает только на ro-mount/БД/обложках.
- Извлечение устройства из любого состояния → `Disconnected`; прерванная операция
  хранится отдельно от состояния и не стирается retry/removal.

## 5. iPod: обёртка libgpod (`crates/ipod`)

Реализует R-06 / W-1..W-7 (`deltas/b007_delta.md`). Свойства:

- Рантайм-загрузка с проверкой ABI при `IpodBackend::load()`; несовпадение — явный
  `BackendUnavailable`, не UB. Доступ сериализован (один mutex вокруг
  load/session/drop).
- Owned-результаты: `DeviceSession` отдаёт `device_info`, `tracks`, `playlists`,
  `artwork_status`, `playback_stats` как Rust-значения — никаких нативных указателей,
  GLib-списков или `GError` наружу; `itdb_free` спарен с drop сессии.
- Артворк честный: `artwork_status()` возвращает вердикт (`Ok` / `Missing` /
  `SkippedUnknownModel`) против независимо посчитанных записей `ArtworkDB`, а не
  полагается на успех `itdb_parse`.
- Чтения доказуемо немутирующие: tree-hash фикстуры; ни один read-путь не зовёт
  `itdb_init_ipod`/`itdb_write*`/создание каталогов.
- Write-API (`create/update/remove`, `write_library`) определён на сессии, но за
  гейтом feature `sync-writes` и недостижим из включённых синк-путей до B-010 (S-20).
- `TrackInfo` несёт `ipod_path` и `mediatype` (raw-биты `mhit` @0xD0) — для smart-оценки
  `VideoKind` (B-008).

Известный долг (B-007, `deltas/b006_delta.md`): константа `LAYOUTS_SHA256`
(`cd93…`) расходится с `sha256sum ffi/layouts.rs` (`7c4b…`) — сверка при следующей
регенерации `layouts.rs`.

## 6. Маппинг `.itl` ↔ iTunesDB (B-008)

Слит в `feature/ipod-page` 2026-11-13. Дизайн, исследования и решения —
`deltas/b008_plan.md`; форматные проверки — `itl-player` `NOTES.md` §20.

- **Идентичность**: PID = `mith` @0x80 = XML `Track ID` = device `mhit` dbid @0x70.
  itl-core 0.1.0 читал PID с неверного офсета (@0x20); исправлено в 0.1.1
  (ветка `fix/itl-core-persistent-id` в itl-player) и поднято в Rufin.
- **Альбомы** — пара (имя, album artist); `album_persistent_id()` (@0x9C)
  задокументирован как непроверенный и не используется.
- **Плейлисты** — матч по (имя, вид); master устройства (`is_mpl`) принадлежит
  устройству. **`mhyp` id @+28 = persistent id плейлиста хоста** (`miph` @+432,
  LE; VERIFIED 2026-11-13: 12/12 устройственных плейлистов против хостовых
  `miph` на паре снапшотов, 6/6 против XML `Playlist Persistent ID` реальной
  библиотеки) — у всех плейлистов, записанных iTunes; только master устройства
  несёт собственный device-authored id. Матч по id с фолбэком на (имя, вид) —
  кандидат на отдельную задачу: переименование в iTunes тогда переживёт синк
  как переименование, а не как удаление+создание. Даты/счётчики сравниваются в
  raw Apple-эпохе, конвертация только на границе записи itl-sync.
- **On-The-Go (OTG)** — плейлист, созданный пользователем прямо на iPod без
  iTunes; часть состояния медиатеки устройства, не просто очередь. Активная
  очередь живёт в `OTGPlaylistInfo` (libgpod отдаёт как `OTG Playlist N`) и
  никогда не кандидат на удаление в любой политике — она не может существовать
  на хосте, пока синк её туда не перенесёт (задача-импорт, отложена). Сохранённый
  OTG (`On-The-Go N` как `mhyp` в iTunesDB, записанный iTunes при импортирующем
  синке) — **обычный плейлист**: синкается в обе стороны, переименовывается и
  удаляется как любой другой; device-only копия следует политике device-only
  (решение владельца 2026-11-13). При записи устройства нельзя сериализовать
  инжектированные libgpod OTG-плейлисты в iTunesDB как `mhyp` и трогать
  `OTGPlaylistInfo`.
- **Файлы**: размер/битрейт на устройстве легитимно расходятся (конвертация в
  AAC-256 у владельца) — совпадение только по идентичности.
- **Smart-правила** (`SLst`, mhoh 0x65/0x66): рекурсивный парсер вложенных групп;
  iTunes уплощает группы при записи на устройство; libgpod 0.8.3 вложенные блобы
  оценивает неверно, поэтому оценщик свой.
- **Оценщик** (`smart::eval_rules`): чистая трёхзначная оценка (`True`/`False`/
  `Undecided`), семантика зеркалит libgpod `itdb_splr_eval` + находки корпуса:
  рейтинг по эффективному значению (fill-down применяет вызывающий),
  boundary-minus-1, `VideoKind` `Is` — битовый тест (это требует факт уплощения
  OR-цепочек в один `BinaryAnd`), `InTheLast` = `date > now + fromdate·fromunits`
  (fromdate = −1), `BinaryAnd`/`NotBinaryAnd` для 0x85; неизвестные поля/действия и
  неизвестные факты = `Undecided`, никогда не тихий false. Media-kind на хостовой
  стороне — `Undecided`, пока не верифицирован офсет mediatype в `mith` (на
  устройстве берётся из `mhit` @0xD0).
- **Поле 0x85** (долг владельца 2026-11-12): гипотеза — purchase/iCloud битовая
  маска, бит 0 = downloaded; подтверждение в бэклоге (проверка в UI iTunes или
  эксперимент с записью на устройство). Маппер представляет его явно и никогда не
  отвергает; переписывание 0x85-правил на устройстве — B-010.
- **Материализованные списки — кэш, не правда.** Критерии — истина, списки членов
  (`mtph`/`mhip`) iTunes пересчитывает при открытии/синке; внеполосные записи
  статистики (itl-sync) оставляют их протухшими в обе стороны. Измерено на паре
  снапшотов: «Хай рейт» — 1820 членов, 2 не проходят собственные критерии
  (raw-rating fill-down), 12 подходящих отсутствуют; «Самые популярные» — правило в
  `.itl` и на устройстве уже «plays > 2», но оба списка держат старые 25 треков
  (1910 подходящих отсутствуют). Обновление списков — бэклог B-021; прошивка
  устройства live-обновляемые плейлисты пересчитывает сама.

## 7. Безопасность данных

Хост (`.itl`):

- Единственная точка записи — itl-sync `sync` (флаги или `--json`-батч, один вызов =
  одна атомарная запись); rolling-бэкапы.
- Отказ по sentinel безусловный, без `--force`-обхода (решение владельца); скан
  `/proc` — второй слой для транзиентного I/O.
- XML никогда не читается как данные; live-`.itl` не трогают ни тесты, ни
  эксперименты (только копии; корпус `iTunesACCEPT` не пишется).
- Работа на копии вне нативной папки библиотеки требует `--media-folder`;
  `on_unmatched=fail` отказывает записи, если любой локализованный трек вне
  media folder.

Устройство:

- Мультифайловое обновление: аудио, `iTunesDB`, `ArtworkDB`, `ithmb`, `Play Counts`.
  `itdb_start_sync()`/`itdb_stop_sync()` на обычных iPod — no-op: ни транзакций, ни
  отката, ни crash-защиты. Поэтому приложение само обязано обеспечить: бэкапы,
  порядок записи, восстановление прерванного синка, исключение конкурирующих
  писателей, безопасный flush/eject (constitution §3, plan «Recovery and
  Statistics»).
- Чексуммы БД — только libgpod; для Classic обязателен корректный FireWire ID,
  иначе библиотека может выглядеть пустой.
- Статистика: перед тем как запись на устройство может потребить `Play Counts`,
  входящие изменения должны быть надёжно сохранены со стабильным маппингом и
  записью дедупликации повторов; числовые dbid могут переприсваиваться и не являются
  единственной идентичностью между синками. Протокол восстановления — B-010.
- До B-010 write-API недостижимы из включённых синк-путей (S-20); «готовность к
  записи» каждой модели проверяется на железе (B-017).

## 8. Тестирование

Env-gated корпуса (ни один тест не трогает продакшн):

- `ITL_TEST_PATH` — копия снапшота `.itl` (паттерн из itl-player; для B-008 —
  `iTunes Library.itl.bak8`-копия, никогда не live-файл).
- `IPOD_TEST_TREE` — снапшот дерева устройства (restored iPod: `iPod_Control/Device`,
  `iTunesDB`, `ArtworkDB`).
- `RUFIN_LIBGPOD_DIR` — префикс пинятой сборки libgpod (по умолчанию
  `/tmp/opencode/libgpod-install/lib`).

Сценарии `scripts/ipod-dev`: `test-synthetic` (ipod-sync + gtk-library без бэкенда),
`test-wrapper` (регрессия обёртки против пинятого libgpod + снапшот),
`lint` (fmt/clippy/rustdoc/diff-check). `scripts/build-libgpod.sh` пересобирает
libgpod 0.8.3 с проверкой всех sha256 и пишет ABI-маркер.

Приёмочные проверки (constitution §4):

- Задачи с записью формата (`.itl`, БД устройства) требуют VM/железо-приёмки до
  мержа: копия `.itl` открывается в настоящем Windows iTunes (чек-лист —
  `itl-player/docs/SETUP.md`); устройство — по каждой поддерживаемой модели
  (B-017): файлы, плейлисты, обложки, чексуммы, round-trip статистики, прерывания,
  безопасное извлечение.
- Никогда: одновременные писатели VM/хоста на одном устройстве, live-`.itl` как тест.
