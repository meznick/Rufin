# Rebase onto upstream/master (0.19 core) — 2026-11-21

## What happened

`fork-master` was 1120 commits behind upstream `master` (the upstream
ref the repo tracked before was a stale `upstream/main`; the real
mainline is `master`). The fork mainline was rebased linearly onto it
(commit `5c085731`), and the fork's features were ported onto the new
core.

## Upstream changes that forced the port

- The seven GTK crates (gtk-shell/gtk-library/gtk-preferences/
  gtk-widgets/gtk-media-menus/gtk-editors/gtk-player) merged into one
  `ui` crate.
- The library was rewritten: `Database` is gone — a thin `Catalog`
  over a `Store`; favorites/outbox deliveries replaced the old
  favorites write path; `user_media_state` became `user_state`;
  `native_media_state` was dropped; listens/play_counts replaced the
  old stats tables; the schema moved to `migration/steps.rs` with an
  image-based snapshot (`load.rs` positional packing).
- The runtime's catalog-notification flow changed: `feed::Feed`
  replaced the `CatalogRevision` watch channel; `SourceEvent` shrank;
  `SourceNotice` is gone.

## What the port changed (fork surface)

- **Schema 66** (`library`): re-added `native_media_state` +
  `itunes_sync_base` (the iTunes write-back slots), a `native_skip_count`
  tracks column, and a `TRACK_EXPLICIT` flags bit (the explicit flag
  rides the flags column so the positional image load stays intact).
  `NativeUserState` + the catalog merge gain `skip_count`; the merge
  SQL compares skips for tracks only.
- **iTunes storage** (`library/src/itunes.rs`): `Catalog` write/read
  API; user ratings go through `favorites::write_user_media_state`.
- **iTunes source** (`sources/src/itunes`): ported to the
  `Observation` model (`start_observation`/`apply_catalog`; completion
  is the wrapper's). Playback goes through the `Source::stream`
  `Implementation::Itunes` arm, which plays the host path the
  observation stored in `track_details.source_path` — the old
  `ItunesSource::stream(database, …)` is gone. `SourceKind::Itunes`
  added.
- **Runtime** (`rufin-core`): `ItunesSync` runs against the `Catalog`
  and posts `SourceEvent::ItunesLibraryBusy`; the playback hook drops
  the removed `scrobbler.listen_recorded`.
- **UI** (`ui` crate): the iPod page/connection/discovery/sync
  boundary live in `ui::library`; `gtk_widgets::`/`gtk_library::`
  paths resolve to `crate::widgets::`/`crate::library::`; the settings
  screen uses `Shell` + `shell.chrome.window`; the star column and the
  explicit badge follow `TrackPresentation` (`TrackRow.explicit`
  comes from the flags bit). The build-time gtk4-builder-tool
  validation moved into `ui/build.rs`; the dead `ipod_monitor` module
  stays out of the build (the owner's decision — direct
  `IpodConnection` with startup + page-open scans).

## Known follow-ups

- The source-setup grouping (device/remote/server boxes on the
  onboarding page) was reverted to master's flat list — port later if
  wanted.
- The itunes integration gates (`ITL_TEST_PATH`) and the iPod
  connection gates (`IPOD_TEST_*`) skip on hosts without the corpora.
- The D-3 `sync-writes` default flip and the build-flag guard remain
  pending per `b017_plan.md` §8.
- **iTunes loudness analysis never runs** (found 2026-11-21, live
  store: `loudness`/`album_loudness` empty, all 3386 tracks selected as
  work, normalization on EbuR128/Track). The EBU R128 pass
  (`rufin-core/src/loudness.rs`) analyzes only playables with an
  `audio_hash`; the hash is computed lazily by `with_audio_hash`,
  which needs the track's `audio_revision` and a local URI
  (`Playable::local_uri`). Only the file walker publishes a revision;
  the iTunes observation publishes neither hash nor revision, and
  `local_uri()` returns None for itunes tracks (it only knows locators
  and Local files rows). The pass silently `continue`s past every
  track, so normalization has nothing to apply. Fix: publish
  `audio_revision` in the iTunes observation from a cheap host-file
  stat (size + mtime, walker-style — no full reads, refreshes stay
  fast), and give `local_uri()` an itunes arm building `file://` from
  `source_path` (same as the stream arm); `with_audio_hash` then reads
  each file once and the pass decodes + measures as a Local library
  does (codecs present on the host: faad, avdec_alac, avdec_aac).
  Cost: one-time read+decode per track, 64-track cancellable batches.
  Tests: corpus-free — an itunes-shaped playable resolves its local
  URI; corpus-gated — observations carry `audio_revision`. Rejected
  alternative: Sound Check gain from the .itl (`mith` @0x58) — read-only,
  dB formula underived (needs a VM experiment), out of scope.
- **Add-to-library (import new tracks)** — specced in itl-player
  NOTES.md §19 «Долгосрочное» (format check; copy into the media
  folder per the iTunes layout when "Keep organized"; new
  `mith`/`mhoh`/`mhgh` elements, `mlth` lists, `mfdh` counters; one
  atomic write with backups; VM acceptance; never `reindex()` — it
  merges the second `mlth`). The Rufin side is not specced yet: the
  import UI (drag-drop/import), the format gate (reuse the Local
  source's codec/container checks), and the writer surface — `itl-core`
  v1 writes stat fields only, so this is the first task that grows the
  writer. First long-term item, before iPod sync.
- **Metadata editing matrix (research)** — for every editable field
  (title, artist, album artist, album, genre, year, disc/track numbers,
  rating, advisory, artwork, loudness) define where an edit lands (file
  tags / the `.itl` / Rufin's DB), who wins on conflict, and how the
  refresh-rescan loop makes it stick. The editor already writes tags to
  the media file for iTunes tracks (registry №16), iTunes re-reads them
  on rescan, and a full file re-scan follows any external `.itl` write.
  Open questions: does iTunes pick up external tag edits without an
  `.itl` write (mtime-based re-read?); `.itc2` cache vs embedded-art
  precedence after a file-art edit; naming (what Rufin does when it
  renames files — the add-to-library layout research feeds this);
  loudness (Rufin's EBU R128 in the DB vs Sound Check in the `.itl` vs
  `iTunNORM` tags — who wins at playback, whether we ever write
  `iTunNORM` back). Deliverable: a spec in itl-player NOTES.md plus an
  implementation plan for the editor's iTunes arm.

## Post-port breakages fixed

Four runtime breaks were found and fixed after the initial port
verification — all four were "data is there, reader looks in the wrong
place" bugs, invisible to a host without the corpus:

1. `no such column: native_artwork` — the artwork blob moved to
   `track_details`; the iTunes artwork query now joins it
   (`7d4efe80`).
2. Missing iPod template — resource path updated to
   `/app/rufin/rufin/ui/routes/ipod_page.ui` (`7d4efe80`).
3. "Track unavailable" on play — the `Implementation::Itunes` stream
   arm read `playable.file` (a `files`-table join only the file walker
   writes); it now plays `playable.source_path` (`555e086a`).
4. Explicit badge always off — `TrackRow.explicit` and
   `TrackFacts.explicit` masked the snapshot record's u16 flags with
   the DB column constant `TRACK_EXPLICIT` (4), which is bit 2 =
   `DELETED` in the snapshot layout; the real bit is
   `snapshot::EXPLICIT` (1<<12). Fixed with a corpus-free regression
   test (`006ffe68`). The now-playing badge was unaffected (it reads
   the details JSON, which keeps the flag).
5. Play/skip counts always 0 on iTunes tracks — `SourceKind::Itunes`
   sat under `file_library()`, and `Context::new` uses that to pick
   whose counts a row shows: file libraries/peers display Rufin's
   listens, servers display the source-reported counts. iTunes is
   file-based but owns its counts (the observation publishes `.itl`
   values + pending growth into `tracks.native_*`, and the listen hook
   bumps the native slots), so every row read the empty listen table.
   `Context` now excludes Itunes from the listened set; `Stats` gained
   `native_skips` (from `tracks.native_skip_count`) because the native
   branch hardcoded skips to 0 — upstream servers have no skip
   concept. Corpus-free regression test in `entities.rs`
   (`eaa45f0b`).
6. Every track duplicated 2× (3386 + 3389 = 6775) — the catalog keyed
   tracks by the numeric `mhoh` id, and iTunes renumbers those on
   re-save (2026-11-21: one re-save shifted every id by +1 — the live
   `.itl` holds #1249 where the store had #1248), so the next refresh
   treated the whole library as new. Fixed by keying on the Persistent
   ID (`mith` @0x80, VERIFIED 3400/3400 vs the XML), with the fresh
   numeric id carried in `TrackMetadata.itunes_track_id` /
   `ItunesPlayerState.track_id` for the write-back (`d01aa3e7`). The
   same pass restored the per-kind completion sweep the port dropped
   (the wrapper completes with an empty kind list — absent rows were
   never unindexed; this also auto-cleans the duplicated rows) and
   fixed the native-slot drift (`record_native_listen` now bumps
   `tracks.native_*`; the flush would otherwise have written a +1
   delta as the absolute `.itl` count). The corpus-gated tests now
   actually run against the live library on this host and pass,
   including a refresh-stability regression test.
7. Eject left a stale Ready page — the unmount succeeded (udisks:
   deactivated cleanly), but the page kept showing the device and a
   second click warned `could not eject ... no mount at`. Cause: B-012
   unwired the gio mount-event monitor (owner decision, mount signals
   never reach rufin on this machine), so nothing drove the FSM back
   to No-iPod — the `eject_device` doc comment still claimed the
   monitor did it. Fixed in the eject handler itself: the button goes
   insensitive while the unmount is in flight and the handler re-scans
   the mount table when it finishes, so a success flips the page to
   No-iPod and a refusal (busy) re-renders Ready with the button
   re-enabled. A mount that vanished underneath us (file manager,
   cable pull) is not logged as a refusal (udisks removes the mount
   point, so `mount_point.exists()` is the check).
